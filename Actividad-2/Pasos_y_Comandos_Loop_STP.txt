1. OBJETIVO DE LA PRÁCTICA
======================================================================

El objetivo de la práctica fue construir en Cisco Packet Tracer una red
con caminos redundantes entre switches, desactivar temporalmente el
protocolo Spanning Tree Protocol (STP) y generar de forma controlada un
Loop de Capa 2.

También se buscó observar el comportamiento del tráfico cuando existe
un circuito cerrado, identificar la multiplicación de eventos ARP e
ICMP y comprobar cómo se recupera la comunicación al retirar uno de los
enlaces redundantes. Finalmente, se documentaron otros procedimientos
para interrumpir el loop, incluyendo el apagado administrativo de un
puerto y la reactivación de STP.

======================================================================
2. ADVERTENCIA Y ALCANCE
======================================================================

La desactivación de STP se realizó únicamente dentro de Cisco Packet
Tracer y con fines académicos. En una red real no se recomienda
desactivar STP cuando existen enlaces redundantes, debido a que un Loop
de Capa 2 puede producir una tormenta de broadcast, duplicación de
tramas, inestabilidad en las tablas MAC, pérdida de paquetes y
saturación de los switches.

Antes de generar el loop se guardó el archivo de Packet Tracer. Además,
la simulación se ejecutó durante un período corto para evitar que la
cantidad de eventos afectara el funcionamiento de la aplicación.

======================================================================
3. DISPOSITIVOS UTILIZADOS
======================================================================

- Tres switches Cisco 2960-24TT: SW1, SW2 y SW3.
- Dos computadoras de Packet Tracer: PC0 y PC1.
- Cinco conexiones Ethernet.
- Cisco Packet Tracer en los modos Realtime y Simulation.

Los switches no necesitaron direcciones IP, ya que fueron utilizados
únicamente para conmutar tramas dentro de la VLAN 1.

======================================================================
4. TOPOLOGÍA Y CONEXIONES REALIZADAS
======================================================================

La topología utilizada fue la siguiente:

                             SW2
                            /   \
                           /     \
                        SW1-------SW3
                         |         |
                        PC1       PC0

Conexiones:

1. PC0 FastEthernet0 con SW3 FastEthernet0/1.
2. PC1 FastEthernet0 con SW1 FastEthernet0/1.
3. SW1 FastEthernet0/2 con SW2 FastEthernet0/2.
4. SW2 FastEthernet0/3 con SW3 FastEthernet0/3.
5. SW1 FastEthernet0/4 con SW3 FastEthernet0/4.

El enlace entre SW1 y SW3 fue el enlace redundante utilizado para
cerrar el circuito. Al conectarlo, los switches SW1, SW2 y SW3 formaron
un triángulo.

Es importante aclarar que una topología triangular no produce por sí
sola una tormenta de broadcast cuando STP funciona correctamente. En
condiciones normales, STP detecta el camino redundante y bloquea uno de
los puertos. Para generar el loop en esta práctica fue necesario
desactivar STP en la VLAN 1.

5. CONFIGURACIÓN DE LAS DIRECCIONES IP
======================================================================

En PC0 se ingresó a Desktop > IP Configuration y se configuró:

Dirección IP:       192.168.1.10
Máscara de subred:  255.255.255.0
Puerta de enlace:   No configurada

En PC1 se ingresó a Desktop > IP Configuration y se configuró:

Dirección IP:       192.168.1.20
Máscara de subred:  255.255.255.0
Puerta de enlace:   No configurada

No fue necesario configurar una puerta de enlace porque PC0 y PC1
pertenecen a la misma red local 192.168.1.0/24.

======================================================================
6. VERIFICACIÓN INICIAL DE LA COMUNICACIÓN
======================================================================

Antes de generar el loop se comprobó que ambas computadoras podían
comunicarse. En PC0 se ingresó a Desktop > Command Prompt y se ejecutó:

ping 192.168.1.20

Este comando envió mensajes ICMP desde PC0 hacia PC1. La recepción de
respuestas confirmó que las direcciones IP y las conexiones iniciales
eran correctas.

La primera solicitud puede tardar más o no recibir respuesta mientras
los dispositivos aprenden las direcciones MAC y se completa la
resolución ARP. Las respuestas posteriores deben recibirse con
normalidad cuando la red no tiene un loop activo.

======================================================================
7. CONFIGURACIÓN DE LOS SWITCHES Y DESACTIVACIÓN DE STP
======================================================================

Los comandos se introdujeron desde la pestaña CLI de cada switch.

Configuración de SW1:

enable
configure terminal
hostname SW1
no spanning-tree vlan 1
end
show spanning-tree vlan 1

Configuración de SW2:

enable
configure terminal
hostname SW2
no spanning-tree vlan 1
end
show spanning-tree vlan 1

Configuración de SW3:

enable
configure terminal
hostname SW3
no spanning-tree vlan 1
end
show spanning-tree vlan 1

Explicación de los comandos:

- enable: permite ingresar al modo EXEC privilegiado.
- configure terminal: permite ingresar al modo de configuración global.
- hostname: cambia el nombre del switch para identificarlo fácilmente.
- no spanning-tree vlan 1: desactiva STP únicamente en la VLAN 1.
- end: regresa directamente al modo EXEC privilegiado.
- show spanning-tree vlan 1: muestra el estado de STP para la VLAN 1.

Después de ejecutar "no spanning-tree vlan 1", el comando de
verificación puede mostrar un mensaje similar a:

No spanning tree instance exists.

Este mensaje indica que no existe una instancia activa de STP para la
VLAN 1. Por lo tanto, ningún puerto redundante será bloqueado
automáticamente.

======================================================================
8. PROCEDIMIENTO PARA GENERAR EL LOOP DE CAPA 2
======================================================================

El procedimiento utilizado fue el siguiente:

1. Se configuraron las direcciones IP de PC0 y PC1.
2. Se comprobó la comunicación inicial con el comando ping.
3. Se guardó el archivo Escenario_Loop_STP.pkt.
4. Se desactivó STP para la VLAN 1 en SW1, SW2 y SW3.
5. Se verificó que STP ya no estuviera activo en la VLAN 1.
6. Se conectó SW1 FastEthernet0/4 con SW3 FastEthernet0/4.
7. El enlace anterior cerró el circuito SW1 -> SW2 -> SW3 -> SW1.
8. Como STP estaba desactivado, todos los enlaces permanecieron
   activos y ningún puerto interrumpió el circuito.

En este punto quedó formado el Loop de Capa 2. El circuito cerrado
permitió que las tramas enviadas por un switch regresaran a él a través
de otro camino y continuaran circulando por la topología.

======================================================================
9. GENERACIÓN Y OBSERVACIÓN DEL TRÁFICO
======================================================================

Para visualizar el comportamiento del loop se realizaron los pasos
siguientes:

1. Packet Tracer se cambió del modo Realtime al modo Simulation.
2. Se seleccionó la opción Edit Filters.
3. Se desmarcaron todos los protocolos.
4. Se dejaron seleccionados únicamente ARP e ICMP.
5. Desde la consola de PC0 se ejecutó:

   ping 192.168.1.20

6. Se cerró o apartó la ventana de la consola para observar la
   topología completa.
7. Se utilizó Auto Capture/Play para avanzar automáticamente la
   simulación.
8. La simulación se mantuvo activa solamente durante unos segundos.

Durante la simulación se observó que las tramas aparecían repetidamente
en los enlaces entre SW1, SW2 y SW3. La lista de eventos aumentó con
rapidez y mostró múltiples eventos ARP e ICMP asociados con los mismos
switches.

La repetición de tramas ocurrió porque el circuito estaba cerrado y no
existía un puerto bloqueado por STP. Las tramas de broadcast podían ser
replicadas y reenviadas por varios puertos, produciendo el
comportamiento de una tormenta de broadcast.

10. PROCEDIMIENTO UTILIZADO PARA ROMPER EL LOOP
======================================================================

El método aplicado en la demostración fue retirar físicamente uno de
los enlaces redundantes. Se realizaron los pasos siguientes:

1. Se pausó Auto Capture/Play para detener temporalmente la simulación.
2. Se seleccionó la herramienta Delete de Packet Tracer.
3. Se eliminó el enlace entre SW1 FastEthernet0/4 y
   SW3 FastEthernet0/4.
4. Al retirar el enlace, el circuito dejó de estar cerrado.
5. Se seleccionó Reset Simulation para limpiar los eventos anteriores.
6. Se ejecutó nuevamente desde PC0:

   ping 192.168.1.20

7. La prueba recibió cuatro respuestas y presentó 0 % de pérdida.

La comunicación continuó por el único camino disponible:

PC0 -> SW3 -> SW2 -> SW1 -> PC1

La recuperación de la comunicación confirmó que el Loop de Capa 2 fue
interrumpido correctamente. La evidencia se guardó como:

Screenshot_Loop_Roto.png

11. MÉTODO ALTERNATIVO: APAGAR ADMINISTRATIVAMENTE UN PUERTO
======================================================================

En lugar de borrar el cable, el circuito también puede abrirse apagando
uno de los puertos que forman el enlace redundante. Por ejemplo, en SW1
se pueden ejecutar los siguientes comandos:

enable
configure terminal
interface fastEthernet 0/4
shutdown
end

El comando shutdown desactiva administrativamente el puerto
FastEthernet0/4. El cable permanece conectado, pero el enlace deja de
transportar tráfico y el circuito se interrumpe.

Para consultar el estado del puerto se puede ejecutar:

show interfaces status

Para volver a habilitar el puerto:

enable
configure terminal
interface fastEthernet 0/4
no shutdown
end

Si STP continúa desactivado y se utiliza "no shutdown", el loop puede
aparecer nuevamente. Por eso, antes de levantar el puerto se recomienda
reactivar STP.

======================================================================
12. MÉTODO RECOMENDADO: REACTIVAR STP
======================================================================

La solución recomendada para conservar el enlace redundante consiste
en reactivar STP. Este procedimiento permite mantener los tres enlaces
físicos, pero bloquea lógicamente uno de los caminos que podrían formar
el loop.

Antes de reconectar o levantar el enlace redundante, se debe habilitar
STP en los tres switches.

Comandos para SW1:

enable
configure terminal
spanning-tree vlan 1
end
show spanning-tree vlan 1

Comandos para SW2:

enable
configure terminal
spanning-tree vlan 1
end
show spanning-tree vlan 1

Comandos para SW3:

enable
configure terminal
spanning-tree vlan 1
end
show spanning-tree vlan 1

Después de habilitar STP se puede reconectar:

SW1 FastEthernet0/4 con SW3 FastEthernet0/4.

Luego se debe cambiar a Realtime y esperar aproximadamente 30
segundos para que STP calcule la topología. Finalmente, se ejecuta:

show spanning-tree vlan 1

La salida debe mostrar los roles y estados de los puertos. Uno de los
puertos redundantes puede aparecer con un estado similar a:

Altn BLK

Este estado indica que el puerto alternativo está bloqueado para evitar
el loop. Si el enlace principal falla, STP puede recalcular la topología
y habilitar el camino alternativo.

No se debe configurar PortFast en los enlaces entre switches, porque
estos enlaces pueden formar caminos redundantes y deben participar en
el cálculo de STP.

14. RESULTADOS OBTENIDOS
======================================================================

- Se construyó una topología redundante con tres switches.
- Se estableció comunicación entre PC0 y PC1.
- Se desactivó STP temporalmente en la VLAN 1.
- Se cerró el circuito entre SW1, SW2 y SW3.
- Se observaron tramas repetidas y un crecimiento rápido de eventos.
- Se rompió el loop eliminando el enlace entre SW1 y SW3.
- Después de retirar el enlace se obtuvieron cuatro respuestas al ping

- Se documentaron el apagado de un puerto y la reactivación de STP como
  métodos adicionales para interrumpir o prevenir el loop.

15. CONCLUSIÓN
======================================================================

La práctica permitió comprobar que una topología con caminos
redundantes puede provocar un Loop de Capa 2 cuando STP se encuentra
desactivado. Al cerrar el circuito entre SW1, SW2 y SW3, las tramas
comenzaron a circular repetidamente y la lista de eventos aumentó con
rapidez.

La eliminación del enlace entre SW1 y SW3 abrió el circuito y permitió
que la comunicación volviera a funcionar de manera estable, con cuatro
respuestas y 0 % de pérdida en la prueba de ping. También se comprendió
que eliminar un enlace resuelve el problema, pero reduce la redundancia
de la red.

STP representa una solución más adecuada porque permite conservar los
enlaces redundantes mientras bloquea lógicamente el camino que podría
producir el loop. Si ocurre una falla en el enlace principal, STP puede
habilitar el camino alternativo y mantener la disponibilidad de la red.
